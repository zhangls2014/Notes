# 项目文档

这里保留当前规范、可重复的操作指南、必要的决策理由和仍有独立价值的调查证据。修改代码时，以当前规范和源码为准；历史调查不能作为当前实现或本次验证的依据。

## 分类与内容归属

| 分类 | 位置 | 保留内容 |
|---|---|---|
| 项目入口 | 根 `README.md`、`AGENTS.md` | 快速开始、执行命令和硬约束 |
| 当前规范 | `architecture.md`、`dependency-upgrades.md` | 当前架构与长期升级规则 |
| 操作指南 | `testing/`，除待验收清单 | 可重复的验证步骤与适用边界 |
| 待验收事项 | `testing/pending-acceptance.md` | 尚未关闭的事项、已有证据与关闭条件 |
| 决策理由 | `decisions.md` | 无法单靠源码恢复的选择理由 |
| 调查证据 | `audits/` | 有独立价值的实验条件、对照与结论 |

已完成的执行计划、被取代的操作命令和无决策价值的流水记录不作为长期文档保留。审计中的历史源码路径与环境只用于还原实验，不作为当前操作入口；已被取代的方案通过 Git 追溯。

## 保留与清理规则

- 当前规则只在对应规范中维护；其他文档通过链接引用，不另存一套现行架构。
- 文档必须至少提供一种价值：当前开发规则、可重复操作、未完成事项，或无法从源码直接恢复的重要决策与实验依据。
- 临时设计和计划仅在需求进行期间保留，可使用 `superpowers/specs/YYYY-MM-DD-<topic>-design.md` 与 `superpowers/plans/YYYY-MM-DD-<topic>.md`。结束或被取代后，将最终约束写入对应规范，必要理由写入 `decisions.md`，未完成事项写入 `testing/pending-acceptance.md`，再清理过程文件。
- 一次性调查放入 `audits/YYYY-MM-DD-<topic>.md`，注明日期、状态、测量条件和验证限制。完成后只保留能避免重复调查的实验、重大版本决策或仍需跟进的证据；普通已完成审计在提炼后清理。
- 新增文档时先判断能否更新现有文件；不为每次小修改永久新增设计、计划和审计三套记录，也不把已完成过程文件全部搬入归档目录。
- 清理前确认原文件已纳入 Git；未提交的独有内容先保存。检查剩余文档的引用和待办没有丢失，再执行删除。删除须遵守 Xander 的授权边界。
- 每个需求结束时检查文档状态；验收完成后更新集中清单中的证据与日期，不把历史通过记录当作当前版本已经通过。

## 文档提交前整理

每次提交包含新增或修改的文档时，必须先按上述分类与保留规则整理受影响文档及其索引、引用和关联状态；需求进行期间的过程提交也适用。

- [ ] 内容放入对应分类；优先更新已有文件，新增或移动文档时同步索引。
- [ ] 清理过时说明、重复内容和无保留价值的流水记录；历史实验保留当时的条件与结论，被取代的操作步骤不混入当前指南。
- [ ] 将有效约束、决策理由和未验收事项分别归入当前规范、决策记录和待验收清单；仍在执行的计划可以保留，已完成的过程记录按保留价值处理。
- [ ] 核对关联文档的状态与描述一致；区分历史证据、本次验证和未验收范围，不把编译通过写成行为或设备验收通过。
- [ ] 检查本地链接、章节锚点、代码围栏，并运行 `git diff --check`；需要历史追溯的删减内容提供可定位的 Git 提交与路径。
- [ ] 删除文件前确认内容已提炼或保存，并取得 Xander 授权；授权未取得时保留文件，在交付中说明待清理项。
